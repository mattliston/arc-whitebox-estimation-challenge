# Linux test bandwidth draft

Provenance: 2026-10-20T20:50:05Z (`date -u`). Source/data inspection only: nothing provisioned, installed, transferred or run remotely. The proposed GCP c4-standard-48 / Ubuntu 22.04 / x86_64 / 180 GB / 250 GB disk configuration is user-supplied and has not been independently checked. Local work continues.

The workload is portable, but the current launcher is not directly runnable on Linux. Keep the estimator and official arithmetic/billing implementation frozen; port paths and passive host monitoring in separate new files. ARM OpenBLAS and x86 OpenBLAS need not produce identical floating-point results. A Linux result must use its own paired Linux baseline before it can support an accuracy claim. Cloud timing cannot establish the public grader's residual margin.

## Calibration required before gains

1. Freeze the **best valid #337393 bank** plus the final empty rescue map as the Linux control. Existing Mac all32 bank science has zero rescue calls, so this source change has a documented ordinary-path equivalence; do not run an adaptive rescue on Linux. Also transfer the frozen disabled micro candidate and both Mac output sets as a second, already-measured bridge. No parameters are fitted during calibration.
2. On a quiet Linux lane, run the original group `[35,150,200]` twice for each frozen source, alternating bank/candidate order across repetitions. Compare within-Linux repeated prediction bytes, actual bills, request counts, product keys and prebind keys. Compare Mac-to-Linux layer outputs and final U. A bill/key discrepancy requires explanation before scaling; investigate any numerical difference larger than repeatability, not merely its sign. Do not claim cross-architecture byte identity in advance.
3. Run all 12 original groups for the bank and the frozen bridge on Linux. Compute each candidate's **paired Linux** adjusted result against the bank on exactly the same ranks and cold/warm positions; report first7 and held25 separately. Compare the Linux candidate/bank contrast to the Mac candidate/bank contrast, with per-rank differences and SE. Do not use the old Mac denominator to grade a Linux candidate, and do not fit against held25. If the bridge changes ordering or bill path, keep cloud results exploratory until the discrepancy is resolved.
4. For each new frozen candidate, compare to that Linux bank using `U = mean((p15-A15)*(p15-B15))` and `100*((U_candidate/U_bank)*(bill_candidate/bill_bank)-1)` **per rank**, then average paired percentages and report SE. Separately report raw, bill, held25 and lower-count. Use the reference judge's float64 evaluation arithmetic. Remote candidate qualification still needs local confirmation and original release gates; a fast VM does not certify platform residual margin.
