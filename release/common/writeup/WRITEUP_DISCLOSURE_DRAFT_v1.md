## Part A — Compliance disclosure (one page)

Written in the order a sponsor reviewer walking the file is likely to meet each item. Factual; nothing here changes the graded outputs.

**A0. Interpreter surface.** The file imports `flopscope`, `flopscope.numpy`, `whestbench.BaseEstimator`, and the stdlib modules `base64`, `zlib`, `time`, `math`, `gc` (lines 1-3, 3856-3857, 6524, 13567, 22032, 22159). There is no numpy/scipy/BLAS, no ctypes/cffi, no threads/asyncio/subprocess/multiprocessing, no exec/eval/compile or runtime code generation, and no file, network or environment access. All numerical work on network data goes through `flopscope.numpy`; Python arithmetic is limited to scalar constants, shape arithmetic, and coefficient tables built once at import from constants (`_np_tables(1024)`, line 11599).

**A1. Inert residual-time governor (dead code; disclosed).** Lines 22136-22250 contain a retired "fast rescue" mechanism from an earlier iteration: `_fast_rescue_live_residual` (definitions at 22168, 22207, 22227; the last is the live name) reads the meter's private attribute `flops._budget._active_context.residual_wall_time_s`, and `_w5_port_begin` (22181-22190) would set `_FAST_RESCUE_ON` for layers listed in `_FAST_RESCUE_FRAC` so that `_shared_old384_mm` falls back to its parent route. This code never executes in the designated submissions: the only caller tests `layer in _FAST_RESCUE_FRAC` before any meter read, and the final statement of the file (line 25741) is `_FAST_RESCUE_FRAC = {}`, so the map is empty for every prediction. Hosted telemetry for the graded runs shows the same operation sequence on every network, consistent with the mechanism being inert. We disclose it because the text of the file reads as a timing-dependent routing switch. In #337641 the block was removed before firing (governor-stripped build, archive e0a79ccb4c52); the inert-code statement above applies to #337619 and #337617.

**A2. Setup-only budget contexts.** Lines 6624 and 7846 open `flops.BudgetContext(flop_budget=2**40, quiet=True, namespace='prebind' | 'g5const')`. They are reached only from the `setup` wrappers (`Estimator.setup` rebindings at 6647 and 7857) and only when the harness raises `NoBudgetContextError` (i.e. setup is running outside a budget context). The work inside them is network-independent: binding of fixed-shape frames and views, and constant tables. `predict` never opens a context of its own; all per-network computation runs inside the grader's context. Setup is off-budget by the evaluation contract: the whest-starterkit estimator contract and FAQ state that `setup(context)` runs once per worker, before any `predict`, outside any BudgetContext, is intended for network-independent precompute, and is limited to 5 s (SETUP_TIMEOUT fails the worker; the clock includes the import). The official rules (§5.5, Phase 2 budget paragraph; verbatim from OFFICIAL_RULES_VERBATIM_PASTE_20261021.md) state: "Separately, a Solution's one-time import and setup phase is subject to its own cap of five (5) seconds. Setup runs once, before any evaluation MLP is assigned, so exceeding this cap fails the entire submission rather than triggering the per-MLP zero-prediction fallback in §5.5." Our setup issues about 14.8k flopscope requests (prebinding of fixed-shape frames, view aliasing, Smirnov plan preparation and constant tables) and completed in 4.10-4.26 s per worker on the hosted graders of #337506, #337565, #337617 and #337619 (local release gates 3.3-3.5 s); one worker of #337534 took 4.66 s and #337614 lost one worker to SETUP_TIMEOUT, which is why the margin is quoted as thin. No computation is hidden in setup: the network is not available to `setup`, every quantity bound there is a function of the fixed 1024x16 geometry alone, and every operation on network data is issued from `predict` inside the grader's metered context.

**A3. Setup wall-clock guard.** During setup the file budgets its own binding work against a wall-clock allowance (`_PB_WALL_S`, 2.8 s; checks at lines 6592, 7141, 7447, 7876 using `time.monotonic()`), so that setup stays under the 5 s cap on slow workers. The clock is never consulted during `predict`, no meter or grader state is read, and the predictions, billed FLOPs, request counts and put counts are byte-identical whatever number of frames setup managed to bind (binding only moves wall time). `_PB_LOG` entries with timestamps are local telemetry.

**A4. Client-side scalars are roster sizes only.** The only values pulled from the meter into Python are integer counts of selected units, `int(fnp.nonzero(...)[0].shape[0])` (lines 441, 5371, 8606, 8909, 9593, 12442, 13582, 16227, 16380, 18036, 24174, 24271). They decide roster sizes (rounded up to multiples of 32/64) — control flow — and at lines 11225-11226 and 12394-12395 the per-column counts enter the sample-size normalisations `1/count` and `sqrt(count-1)` that are then applied with metered ops. This is arithmetic on count metadata (the same class as a 1/sqrt(n) factor), not on array values, and it is the entirety of the residual-time computation beyond control flow.

**A5. Shadowed definitions.** The basis routine `_rtt_basis` is defined three times (18003, 18095, 18167); Python's name resolution makes the last definition the live one. The live version computes norms with the metered `fnp.linalg.norm`, materialises the scalar only for a rank test, and divides the vector by it with a metered op. The two earlier, superseded definitions contain a Python `**0.5` on a materialised sum; they are never called. Likewise the three definitions of `_fast_rescue_live_residual` (A1). These are artefacts of the append-only build process and will be pruned in any further file.

**A6. Exact-arithmetic kernels and price-aware comments.** The bill reductions in this lineage come from algorithms that perform fewer arithmetic operations, each sub-operation metered at its own cost: Strassen/Winograd-type recursive products and grouped ("Smirnov") reads for the third-order plane bank; padding of some products up to kernel-eligible shapes (`_O18PAD_RULES`, line 24065; nominally more work, fewer metered multiplies); selection among exact routes by metered FLOPs saved per added request (`_O18_REQUEST_PENALTY`, line 23677, and the peel/shared/fusion budgets); the upper-half symmetric Gram product (`_O20_GRAM_ON`, 24643); float32 instead of float64 for the mean and b-carrier transports (`_O20_MU32/_O20_B32`, 24657-24658); a cached zero scalar (20108); and a rational nonlinearity in the learned edge module in place of tanh (`_O20_ECUT_RADICAL_*`, 25356-25359), which changes the estimate and was measured as such. Comments in the file refer to prices and price screens because the team chose among exact alternatives by their metered cost; none of these transformations re-expresses an identical operation through a differently-priced primitive, and every one is either exact or a measured approximation that is part of the method.

**A7. Scatter-for-gather retired.** Earlier files gathered rows by a scatter primitive at nine sites (`_xsg_rows`/`_xsg_cols`, gated by `_XSG_ON`). In the designated submissions `_XSG_ON = set()` (line 25740), so every gather is a plain index `A[idx]`; predictions are byte-identical and the bill is 0.077% higher than the gated version. We treat the gated form as falling under §5.5 (a transformation whose only purpose is a cheaper-charged path) and did not designate any file that uses it.

**A8. Rebinding is on our own objects.** The many `Estimator.predict = ...` / `Estimator.setup = ...` statements rebind methods of our own subclass (`class Estimator(BaseEstimator)`, lines 589/796/1078), never the harness class. During setup the module alias `fnp` is temporarily replaced by a local facade (`_SetupAliasHold`, 21786/22002; swap and restore at 21808-21822) that records view operations so their handles stay bound; it calls the flopscope functions unchanged and is removed in a `finally`. No attribute of `flopscope`, `flopscope.numpy` or `whestbench` is assigned, deleted or wrapped in place.

**A9. Garbage-collector control.** Lines 22039-22069 freeze the setup graph and raise the gen-2 threshold during `predict`, restoring the previous settings afterwards (`gc.freeze/collect/disable/set_threshold`). This is interpreter plumbing that reduces residual time; it performs no computation.

**A10. Embedded data.** Model coefficients (the per-layer readout heads, edge parameters, dial tables, Smirnov plan tables) are embedded as base64+zlib float32 literals, decoded into flopscope arrays by `_unpack_static_fp32` (line 3859) at import. The random projection used by the join sketch uses a fixed seed (`_LR_SEED = 20260924`, lines 6667/6675). The file reads only `mlp.width`, `mlp.depth` and `mlp.weights`; no network identifier, seed or hash enters any table or branch.

## Part B — Algorithmic write-up skeleton (1-2 pages; due 24 Oct 2026)

### B1. Problem and score
Estimate the final-layer output statistics of 1024-wide, 16-deep MLPs (dataset v2-phase2) without sampling; score = final-layer MSE x compute utilisation (metered FLOPs / 2^41), lower is better; 120 s wall and 0.4 s residual caps per network, 5 s setup cap. [lead: one paragraph on what "final-layer MSE" is scored against, per the rules.]

### B2. Method summary
1. **Closure card (cumulant propagation).** Per-layer propagation of per-unit pre-activation means, variances and third/fourth cumulants with a carried covariance structure; the dominant terms are the third-order "plane bank" (pushed and read at every layer, ~80% of the bill), the pair map, birth terms for newborn directions, a dead-cut star, and row cuts at the terminal layer. [lead: cite the mechanistic decomposition notes; keep to the shipped form, no phase-1 numbers.]
2. **Exact kernels for the bill.** Strassen/Winograd-type products, grouped Smirnov reads, Nystrom join sketch on the heaviest joined columns (`_JSK_KC` 1536/1024/1024), symmetric Gram, f32 transports — all exact or measured, see Part A6.
3. **Learned per-layer correction (readout).** A small GNN-style correction per layer (state 64, hidden 128) reads per-unit features of the propagated state and adds a scaled correction to the layer's mean; coefficients are data literals.
4. **On-policy second-step readout (today's gain).** The deployed readout heads were refit on captures of the deployed file's own trajectory on 90 training networks: design = 705-column "gate" readout (state, hidden2, first128, squares, first128 x gate) plus the hidden2 x gate block ("hg") and the first128 x hidden2 block ("fh"), 961 columns in total; ridge 0.03, damping 0.5, five-fold held-18 validation with seals before the held sets; exported as float32 head rows 1..15 plus one step override (`_gop2_gnn_step`, line 25690). Strength (shrinkage) scalar x1.5 on the deployed files; x1.35 measured better on the 961-column seal (see B3).
5. **Wall-margin tail.** Smirnov young-read cap of 4 per prediction plus dropping the 9 plans with m·k·n ≥ 8e9 (`_SM40_CAP`, `_ASTRA_SM40_PLANS` wrapper, lines 25728-25738): bill +0.18%, raw MSE unchanged, hosted wall about -5 to -6%, residual -3 to -5%. Chosen so the slowest public network stays ~10 s under the 120 s cap after #337534 failed on grader jitter.
6. **Fair accounting.** XSG off in all designated files (A7).

### B6. LLM-assistance transparency statement
The official rules (§5.7, verbatim from OFFICIAL_RULES_VERBATIM_PASTE_20261021.md) state: "Use of external resources. Participants are encouraged to use public resources to build their Solutions. Use of LLMs (including code-assistant tools and general-purpose LLMs) to write code is allowed. Where a technical writeup is submitted under §6, the Participant must be fully transparent about the extent to which LLMs were used to generate the Solution code or any portion of the writeup. Where a Participant has significant uncertainty about how or why their code works, the relevant portions of the writeup must be hedged accordingly or labelled as guesswork. Used datasets, libraries, or pre-existing code must be publicly available and equally accessible to all Participants. Award winners may be required to make any private resources or re-formulations publicly available after the Competition."

Disclosure: this entry was developed with extensive use of large-language-model coding agents. The team member (Matt Liston) directed the work through Claude Code sessions in which Anthropic Claude models (Claude Fable 5.1 as the lead agent, with Claude Opus and Claude Sonnet teammate agents) wrote and edited the estimator source, ran and analysed the local measurements, and drafted this document, and OpenAI Codex agents ran parameter sweeps and some earlier builds. Every submitted estimator is a single Python file authored in those sessions; it computes exclusively through the flopscope client API with the Python standard library for control flow, was gated locally (32 paired store networks, fresh networks, and the release gates for setup time, residual, request counts and operation signatures) before each fire, and was fired on the team member's explicit instruction, who takes responsibility for its content. No LLM or external service is invoked at setup or prediction time; the submitted files contain only Python source and embedded numeric data.

Hedging, per the last requirement of §5.7. We understand the mechanism of the moment-closure card: it propagates per-unit means, variances and third/fourth cumulants with a carried covariance structure and third-order plane terms through the ReLU map, and its remaining error is characterised (final-layer MSE is about 79% inherited from the layer-14 means, the late covariance error is a self-consistent chain, and the per-unit residual is unbiased noise at about 1e-4 relative). We also understand the exact kernels (they are algebraic identities verified byte-for-byte or at rounding level) and the measured dials, whose values were set by finite-difference line searches on held-out networks and whose individual effects are reported in B4. The parts we do NOT fully understand and label as empirical are: (i) the learned per-layer correction and in particular the on-policy second-step readout of B2.4, which is a ridge regression fitted to captures of our own deployed trajectory on 90 training networks; we know that it lowers the final-layer error on held-out store and fresh networks and on the hosted public set, and that its strength optimum sits near x1.35, but we have not derived why its specific feature blocks (hidden2 x gate, first128 x hidden2) carry the gain, nor why physics dials that help the base file stop helping once the readout is present beyond the general statement that the readout is co-adapted to the trajectory it was fitted on; (ii) the choice of the particular dial values, which are fitted rather than derived. Generalisation of the readout was checked only on held-out store networks, 12 fresh networks and the public evaluation set; its behaviour on the private re-evaluation suite is extrapolated from those.
