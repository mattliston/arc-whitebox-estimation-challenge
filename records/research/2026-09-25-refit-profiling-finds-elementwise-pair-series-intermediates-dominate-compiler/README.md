# Refit profiling finds elementwise pair-series intermediates dominate; compiler fusion unavailable

2026-09-25T02:09Z · finding · informational · measured

The differentiable pair map materializes large float64 series tensors and spends little time in matrix multiplication. A minimal compiler-fusion attempt hung or exited, motivating explicit series restructuring.

Recorded measurement:

    - 2026-09-24 19:09 [engineer] REFIT STEP PROFILE (E-64; refit_step_profile.py + refit_fn_timing.py, S18-physics torch card, fine_ckpt, full+P, net 37, 3 threads, load 12): forward no-grad 8.7 s, forward+grad 9.1 s, backward 31.8 s (~41 s/net, ~1.8 h per 160-net epoch). Self CPU: elementwise mul 36% (27k calls) + sum/add/copy/fill/div ~25%; matmul only 6%. By function (forward): _nonlinear_pair_batch incl. _pair_series_fused = 41% (no grad) / 47% (grad) on float64 [3,3,1024,1024] tensors (memory-bound); push+read+star ~13%. Lever: fuse the pair map (torch.compile on that env function; float64 kept) ~-25..-30% per step if backward follows; offered to prototype in my folder pending GO.
    - 2026-09-24 19:19 [engineer] REFIT FUSION via torch.compile: UNAVAILABLE on this machine (anaconda torch 2.7.0, macOS): a minimal float64 elementwise function hung in inductor's compile workers, and died silently with TORCHINDUCTOR_COMPILE_THREADS=1. The remaining refit-speed lever is restructuring the pair map's 3x3 series (_pair_series_fused / _nonlinear_pair_batch) to accumulate term by term instead of materializing [3,3,1024,1024] float64 intermediates (likely -20..-30% per step); that is the physics owners' shimmed native code, so not touched without them.
